# 정답지 루프 — "사장님이 답을 주면, 기계가 고칠 수 있는 것은 기계가 다 고친다"

> 작성: 2026-09-02
> 기준 커밋: `JINOI/main` = `bf7c8df`
> 관련: `plan.md` §1(판정 개선 루프)·T11(파인튜닝), `CLAUDE.md`

## 1. 이 문서가 푸는 문제

지금까지 `plan.md` §1의 루프는 **사람이 사진을 보고 → 사람이 원인을 짚고 → 사람이
무엇을 고칠지 정하는** 방식이었다. 10바퀴를 그렇게 돌았다.

문제는 **사장님에게 물어보는 횟수**다. 오답 하나하나마다 "이건 왜 그럴까요"를
물으면, 정작 사장님만 답할 수 있는 질문(파인튜닝을 할 것인가, 엣지 예산을 쓸
것인가)이 잡음에 묻힌다.

**이 문서가 정하는 것**: 사장님은 정답지 한 장만 준다. 그다음부터는 기계가
자기 힘으로 고칠 수 있는 것을 전부 고치고, **정말 사람 손이 필요한 것만 남겨서
보고한다.**

## 2. 정답지 형식

`results/angle1_layout/정답지.md` — 사람이 손으로 쓴다.

```
1번 사진 (0초)
- T1 : 사용중
- T2 : 빈자리
- T4 : 사용중 ← 책상에 노트북 있는데 우리가 못 잡음
- BAR7-4 : 모름 ← 사람이 완전히 가림
```

- 상태 어휘는 셋 — **사용중 / 빈자리 / 모름**. `←` 뒤의 이유는 틀린 자리에만 단다
- **`모름`도 정답이다.** 사람 눈으로도 안 보이는 자리를 억지로 둘 중 하나로
  고르게 하면, "가림이 상시적"(`CLAUDE.md`)인 1대 화각에서 달성 불가능한 목표를
  세우게 된다. 목표는 UNKNOWN 0이 아니라 **정직하지 않은 UNKNOWN 0**이다
- 좌석 이름은 대소문자·공백을 가리지 않는다 (`BAR7-4` `Bar7-4` `bar7-4`)
- **6장 × 12자리 = 72칸이 다 찼는지 채점 전에 검사한다.** 안 적은 칸을 "맞음"으로
  가정하면 회귀를 못 잡는다

## 3. 설계의 핵심 — 두 겹으로 채점한다

이 문서에서 가장 중요한 결정이다. 이걸 안 하면 **채점기가 좋은 규칙을 망가뜨린다.**

정답지는 "그 순간 실제로 어떤 상태인가"다. 그런데 우리 판정에는 **확정 지연**이
있다 (점유 2번 / 빈자리 3번 확인 후 확정, `plan.md` §3).

> 15초에 T3 의자에 가방이 **처음** 보였다.
> 정답지: **사용중**. 우리: **모름** — 근거는 제대로 봤고, 한 번 더 봐야 확정한다.

이건 오답이 아니라 **규칙대로 동작한 것**이다. 이걸 오답으로 세면 점수를 올리려고
확정 지연을 없애는 쪽으로 "고치게" 되고, 그건 **손님을 남의 자리로 보내는** 규칙
완화다.

로그에는 이미 두 값이 있다. 둘 다 채점한다.

| 로그 필드 | 뜻 |
|---|---|
| `raw_state` | **이번 판단에서 실제로 본 것** |
| `state` | 시간 로직(확정·유지)을 통과한 최종 = 손님 앱에 나가는 답 |

| 앱 답(`state`) | 근거(`raw_state`) | 뜻 | 고치나 |
|---|---|---|---|
| ✅ | ✅ | 완전히 맞음 | — |
| ❌ | ✅ | **지연** — 근거는 맞게 봤는데 아직 확정 전 | ❌ 정상 동작. 개수만 센다 |
| ✅ | ❌ | **유지** — 이번엔 못 봤는데 과거 근거로 버텼다 | ⚠️ 낮은 우선순위 |
| ❌ | ❌ | **진짜 오답** | ✅ 최우선 |

### 오답의 방향도 같이 붙인다

| 방향 | 뜻 | 심각도 |
|---|---|---|
| `놓침` | 우리 빈자리, 정답 사용중 | **제일 나쁨 — 손님이 남의 자리로 간다** |
| `헛것` | 우리 사용중, 정답 빈자리 | 나쁨 — 빈자리를 못 찾는다 |
| `과잉모름` | 우리 모름, 정답은 확정 | 정보 손실 |
| `과소모름` | 우리 확정, 정답은 모름 | 근거 없이 단정 |

## 4. "이건 파인튜닝 영역인가"를 증거로 가른다

우리 로그(`raw_detections`)는 **이미 신뢰도 0.15로 걸러진 뒤**다. 그래서 로그만
보면 "모델이 0.05로는 봤다"를 "모델이 못 봤다"로 잘못 분류하고, **임계값만 내리면
잡히는 것을 파인튜닝 숙제로 넘긴다.**

대신 **오답 난 자리만** 골라 이미 저장돼 있는 `clean/*.jpg`를 **신뢰도 0.01로 재추론**
한다. 영상 재디코딩이 없어 사진 6장이면 몇 초다. 세 갈래로 갈린다.

| 딱지 | 조건 | 처리 |
|---|---|---|
| **로직** | 우리 임계값(0.15) 위에서 이미 잡혀 있었다 | **코드가 버린 것.** 기계가 고친다 |
| **임계값경계** | 0.01~0.15 사이에서만 보인다 | 전역 임계값을 내려보고 **72칸 전체 점수가 좋아지면 채택, 나빠지면 파인튜닝으로 강등** |
| **파인튜닝** | 0.01에서도 안 보인다 | **모델이 진짜 못 본다.** 기계 손을 떠난다 |

사람 관련 오답은 **자세 모델도 같이** 본다 — "사람을 못 잡았다"와 "사람은 잡았는데
자세를 못 읽었다"는 다른 숙제다.

진단기의 설정(모델 경로·`imgsz`·임계값)은 **`log.jsonl`의 `run` 기록에서 읽는다.**
플래그로 따로 주면 진단이 실제 실행과 조용히 어긋난다.

| | 무엇 | 모델 |

앞의 둘은 **모델·GPU 없이 도는 순수 로직**이다 (이 저장소의 테스트 556개가 그렇듯).
그래서 회귀 테스트를 붙일 수 있다. 진단기만 모델을 쓴다.

## 6. 루프를 도는 절차 (`/seat-loop` 스킬)

```
실행 → 채점 → 진단 → '로직' 오답 하나 고침
  → 회귀 테스트 + 72칸 전체 재채점
  → 나빠졌으면 되돌림 → 다음 오답
```

**한 번에 하나만 고친다.** 둘을 같이 고치면 어느 쪽이 점수를 올렸는지 알 수 없고,
하나가 다른 하나를 망가뜨려도 안 보인다.

### 기계가 물어보지 않고 바꿔도 되는 것 (사장님 승인, 2026-09-02)

- ✅ 판정 규칙 구조 자체
- ✅ 전역 임계값 숫자 (매장별 튜닝이 아니라 **전역 기본값 하나**를 옮기는 것)
- ✅ 좌석 상자 다시 그리기 (`layouts/cafe_angle1.json`) — 바꾸면 사진으로 전후를 보인다
- ❌ **`imgsz` 상향은 하지 않는다** (2026-09-02 결정). 정확도는 오르지만 엣지 계산량이
  늘고, 박스가 안 와서 예산을 모른다. 모델 크기 상향(`yolov8n` → `yolov8x`)도 같은 이유로
  기계 권한 밖이며, 필요해지면 보고 항목으로 올린다

### 과적합 방지 — 사진 6장에 코드를 맞추지 않기

`plan.md` §6이 이미 경고했다. 4.8분짜리 영상에는 A/B 차이를 가릴 통계력이 없다.

- 수정마다 **72칸 전체**를 다시 잰다. 한 칸 살리려다 두 칸 죽이면 되돌린다
- 실패 사례의 **실제 좌표로 회귀 테스트**를 추가한다 (저장소 관례)

  설명돼야 한다

## 8. 이 설계가 감수하는 것

- **정답지 한 장(72칸)은 통계적으로 약하다.** 여기서 나온 임계값은 "이 영상에서
  틀리지 않는 값"이지 "옳은 값"이 아니다. 각도가 확정되고 `T16` 라벨이 나오면
  다시 재야 한다
- **`모름`을 정답으로 인정하면 UNKNOWN을 줄일 압력이 약해진다.** 대신 사유 코드
  분포가 남으므로, 어느 사유가 몇 칸을 먹고 있는지는 계속 보인다
  (`CLAUDE.md`: "사유별 분포가 곧 다음 개선 백로그다")
- **진단기의 딱지는 기계적이다.** "0.01에서도 안 보인다"가 곧 "파인튜닝하면 잡힌다"는
  뜻은 아니다. 근본적으로 안 보이는 각도일 수도 있고, 그건 설치 문제다(`CLAUDE.md`)
