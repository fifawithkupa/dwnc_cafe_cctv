# 엣지 박스 첫 실행 — OptiPlex 7040 Micro (i3-6100T · Linux)

> 작성: 2026-09-02
> 대상: **Dell OptiPlex 7040 Micro / Core i3-6100T / RAM 4GB / Linux**
> 긴 절차(카메라 고르기까지)는 `docs/edge-setup.md`. **이 문서가 먼저다.**

## 목표는 딱 하나

**지금 노트북에서 돌아가는 로직을, 손대지 않고 이 박스에서 끝까지 돌린다.
그리고 "판단 한 번에 몇 초 걸리는가"를 숫자로 얻는다.**

합격선은 **7.5초**다 (판단 주기 15초의 절반). 여유 절반을 요구하는 이유는
24시간 도는 박스에 스트림 재연결·디코더 리셋·로그 정리가 언제든 끼어들기
때문이다.

### 이번에 하지 않는 것 — 미리 알아야 실망하지 않는다

- **카메라는 안 꽂는다.** 지금 코드는 **녹화 파일 전용**이고, 라이브 스트림
  읽기는 아직 없다 (`plan.md` T8). 카메라를 꽂아도 안 돈다
- **어떤 카메라를 살지도 안 고른다.** 그건 `docs/edge-setup.md`의
  `bench_decode` 단계이고 이 문서 다음이다

### 이 박스에 대해 미리 아는 것

| | |
|---|---|
| CPU | i3-6100T — **연산 코어 2개** (논리 4개는 하이퍼스레딩), 3.2GHz, 2015년 Skylake |
| 내장 그래픽 | Intel HD 530 — **지금은 놀고 있다.** 5단계 ②에서 쓴다 |
| RAM | 4GB — 빠듯하다 (아래 경고) |
| 예상 | **지금 설정 그대로면 틱당 13~20초.** 15초 주기를 못 지킨다 |

**놀라지 말 것.** 5단계에 시간을 절반 이하로 줄이면서 정확도를 안 깎는
카드가 있고, 첫 장은 공짜다.

> **리눅스로 간 것은 잘한 선택이다.** 속도 때문이 아니라 두 가지 때문이다 —
> ① 윈도우는 새벽에 강제 업데이트로 재부팅하고 로그인 화면에서 멈춘다.
> 무인 박스가 그러면 아침에 좌석 정보가 죽어 있다 ② **윈도우보다 RAM을
> 1~1.5GB 덜 먹는다.** 4GB에서는 이게 결정적이다.

## 0단계 — 박스 확인 (30초)

```bash
lscpu | grep -E "Model name|^CPU\(s\)|Core\(s\) per socket|Thread"
free -h
df -h /
python3 --version
```

| 항목 | 필요 | 안 되면 |
|---|---|---|
| 디스크 여유 | **10GB 이상** | 정리한다. 모델·라이브러리로 2GB 넘게 쓴다 |
| `python3 --version` | **3.11** | 노트북과 같은 버전이라 이 조합만 실제로 검증됐다. 3.12(우분투 24.04)에도 필요한 파일은 다 있는 것을 확인했지만 돌려본 적은 없다. 판정이 노트북과 다르게 나오면 이걸 먼저 의심한다 |

## 1단계 — 설치

```bash
sudo apt update
sudo apt install -y python3-venv python3-pip git ffmpeg \
    intel-media-va-driver-non-free vainfo
```

> ⚠️ **`-non-free` 가 붙은 쪽이어야 한다.** 이름만 비슷한
> `intel-media-va-driver` 는 기능이 빠져 있다. 이게 HD 530의 하드웨어
> 디코딩(Quick Sync)을 켜는 드라이버이고, **없으면 영상 푸는 데만 CPU를
> 3~6배 더 쓴다.** 연산 코어가 2개뿐인 박스에서는 치명적이다.

**드라이버를 깔았어도 권한이 없으면 안 켜진다.** 리눅스에서 내장 그래픽은
`/dev/dri` 라는 장치 파일로 접근하는데, 여기에 들어갈 수 있는 사람은
`render`·`video` 그룹에 속한 계정뿐이다. 아니면 `vainfo` 도 ffmpeg 도 조용히
실패하고 소프트웨어 디코딩으로 떨어진다 — **드라이버 탓으로 착각하기 딱 좋다.**

```bash
sudo usermod -aG render,video $USER
```

⚠️ **이 명령 뒤에는 로그아웃했다가 다시 로그인해야 적용된다.** (`groups` 로
`render` 가 보이면 된 것이다.)

확인 — `VAProfileH264...` 같은 줄이 나와야 한다:
```bash
vainfo
```

저장소와 파이썬 환경:
```bash
cd ~
git clone https://github.com/fifawithkupa/dwnc_cafe_cctv.git seatnow
cd seatnow
python3 -m venv venv
./venv/bin/python -m pip install --upgrade pip
./venv/bin/python -m pip install -r requirements-edge.txt
```

> ⚠️ **`requirements.txt` 가 아니라 `requirements-edge.txt` 다.** 두 가지가 다르다.
> ① **노트북과 똑같은 버전**을 깐다. 4단계에서 "엣지도 70칸인가"를 볼 건데,
> 라이브러리가 다르면 답이 달라도 그게 박스 때문인지 버전 때문인지 모른다
> ② **torch 를 CPU 판으로 받는다.** 그냥 받으면 리눅스에서는 엔비디아 GPU용
> (CUDA) 판이 내려와서, 이 박스에서 한 번도 안 쓰이는 파일로 디스크를
> 2~3GB 더 먹는다

설치가 끝나면 CPU 판이 맞는지 확인한다 — **끝에 `+cpu` 가 붙어야 한다**:

```bash
./venv/bin/python -c "import torch; print(torch.__version__)"
# 2.2.2+cpu
```

`sample_raw/` 는 저장소에 없다 (용량·개인정보). **`cafe_sample_angle1.mov`
하나만** 있으면 된다 — **146MB**. 나머지 영상은 이번에 필요 없다.

```bash
mkdir -p ~/seatnow/sample_raw
```

리눅스에는 구글 드라이브 데스크톱 앱이 없다. 다른 PC에서 받아 옮긴다:

```bash

scp cafe_sample_angle1.mov <사용자>@<박스IP>:~/seatnow/sample_raw/
```

USB로 옮겨도 된다. AI 모델(13MB)은 **처음 실행할 때 자동으로 받아진다.**

## 3단계 — 검수

**영상을 넣은 뒤에 해야 한다.** `--sample` 을 빠뜨리면 이 박스에서 가장
중요한 항목인 하드웨어 디코딩을 확인하지 못한다.

```bash
./venv/bin/python -m edge.check_edge --sample sample_raw/cafe_sample_angle1.mov
```

### 여기서 볼 것은 둘뿐이다

**① 하드웨어 디코딩이 "꺼짐"이면 멈추고 드라이버부터 잡는다.**
꺼진 채로 재면 실제보다 훨씬 나쁜 숫자가 나와서, 멀쩡한 박스를 못 쓴다고
잘못 판단하게 된다.

**② "CPU 코어 수: 4개 합격"은 무시한다.**
그 도구는 **논리 코어**를 센다. i3-6100T는 하이퍼스레딩이라 4개로 잡혀
합격이 뜨지만 **실제 연산 코어는 2개다.** AI 추론처럼 코어를 꽉 채워 쓰는
일에서 하이퍼스레딩은 코어 2개 몫을 못 한다 (보통 1.2~1.3배).
**이 박스의 진짜 판정은 검수 화면이 아니라 4단계의 실측 숫자다.**

> **RAM 4GB도 "합격"이 뜬다** (합격선이 정확히 4.0GB라서). 리눅스라 윈도우보다
> 낫지만, 파이썬+AI 모델이 1.5~2.5GB를 쓴다. 데스크톱 없이 서버로 설치했다면
> 아마 될 것이고, 데스크톱 환경이면 빠듯하다. **틱 시간이 들쭉날쭉하면
> (어떤 틱은 4초, 어떤 틱은 20초) CPU가 아니라 RAM 문제다** (5단계 ③).

## 4단계 — 진짜 실행 ⬅️ **오늘의 목표**

노트북에서 돌리는 것과 **한 글자도 다르지 않은 명령**이다.

```bash
./venv/bin/python -m engine.seatnow sample_raw/cafe_sample_angle1.mov \
  --layout layouts/cafe_angle1.json \
  --log results/edge_angle1/log.jsonl \
  --frame-dir results/edge_angle1 \
  --log-detections --no-video
```

이런 줄이 6개 나온다. **맨 뒤 `inference=` 가 오늘 얻으려는 숫자다.**

```
[  0.0s] tables=12 occupied=3 empty=8 ... inference=3488ms
```

| 나온 값 | 뜻 |
|---|---|
| **7500ms 이하** | ✅ 합격. 이 박스로 간다 |
| 7500~15000ms | ⚠️ 돌긴 하는데 여유가 없다 → 5단계 |
| **15000ms 초과** | ❌ 주기를 못 지킨다 → 5단계 |

참고: 개발 노트북(Core Ultra 5 226V, 2024년, 8코어)에서 **3.3초**다.

### 답이 같은지가 속도보다 먼저다

장비가 달라도 **판정은 똑같아야 한다.**

```bash
cp results/angle1_layout/angle_answer.md results/edge_angle1/
./venv/bin/python -m checks.score_answers results/edge_angle1 \
  --answers results/edge_angle1/angle_answer.md --title "엣지 박스"
```

**`accepted=70`, `wrong=2` 가 나와야 한다.** 노트북과 같은 값이다.
다르면 속도를 논하기 전에 그것부터 본다 (보통 라이브러리 버전 문제다).

## 5단계 — 7.5초를 못 지켰을 때

**순서대로 하나씩. 그리고 매번 4단계의 채점을 다시 돌린다.**
한 번에 여러 개를 바꾸면 무엇이 효과가 있었는지 모르고, 빨라진 대신 손님을
남의 자리로 보내면 아무 의미가 없다.

### ① 버스트 5프레임 → 3프레임 — 공짜다. 이것부터

판단 한 번에 연속 5프레임을 보고 다수결하는데, **3프레임으로 줄여도
정답지 72칸이 그대로다.**

```bash
--median-frames 1
```

노트북에서 잰 표다 (정확도는 같은 정답지 72칸 기준).

| 버스트 | 크롭 | ms/tick | 옳음/72 | 오답 | 지금 대비 |
|---:|---:|---:|---:|---:|---:|
| 5프레임 | 4 | 3276 | **70** | 2 | 100% (지금) |
| **3프레임** | **4** | **1920** | **70** | **2** | **59%** ⬅️ 공짜 |
| 5프레임 | 2 | 2076 | 69 | 3 | 63% |
| **3프레임** | **2** | **1265** | **69** | **3** | **39%** |
| **3프레임** | **1** | **977** | **69** | **3** | **30%** |
| 1프레임 | 4 | 750 | **56** | 4 | 23% |

> **1프레임은 절대 안 된다.** 70칸 → 56칸으로 무너진다. 여러 프레임 다수결이
> 실제로 일을 하고 있다는 뜻이다. **3프레임이 바닥이다.**

⚠️ 이 표는 **6틱(78초)** 에서 나왔다. 다수결은 탐지가 순간적으로 흔들리는
것을 막는 장치인데 78초에는 그런 흔들림이 몇 번 없다. **긴 영상이 생기면
3프레임이 여전히 안전한지 다시 확인해야 한다.** 그래서 기본값은 5프레임으로
두고, 엣지에서 필요할 때 켜는 옵션으로 남겼다.

### ② OpenVINO — 공짜 소프트웨어. 이게 가장 크다

**장비가 아니다.** 인텔이 무료로 주는 번역기로, 우리 AI 모델을 인텔 칩이
알아듣는 형태로 다시 쓴다. **같은 모델, 같은 판정, 같은 정확도 — 더 빨리
돌기만 한다.** 그리고 **놀고 있는 내장 그래픽(HD 530)까지 같이 쓴다.**

```bash
./venv/bin/python -m pip install openvino
./venv/bin/python -m edge.export --precision fp32 --imgsz 1280
```

`yolov8n_openvino_model/` 과 `yolov8n-pose_openvino_model/` 폴더가 생긴다.
실행할 때 모델만 바꿔 끼운다:

```bash
./venv/bin/python -m engine.seatnow sample_raw/cafe_sample_angle1.mov \
  --layout layouts/cafe_angle1.json \
  --det-model yolov8n_openvino_model \
  --pose-model yolov8n-pose_openvino_model \
  --log results/edge_ov/log.jsonl --frame-dir results/edge_ov \
  --log-detections --no-video
```

보통 2~4배 빨라진다고 알려져 있지만 **6세대 Skylake + HD 530에서 얼마가
나올지는 이 명령이 알려준다.**

> **왜 `--imgsz 1280` 하나만 뽑나 (2026-09-03 수정)**
> 판단 한 번에 검출 모델이 **두 가지 크기로** 불린다 — 화면 전체는 1280,
> 테이블 크롭은 960. 그래서 크기를 하나로 못 박은 모델은 애초에 한 틱을
> 감당하지 못한다. 지금 `edge.export` 는 **어떤 크기든 받는 모델**을 뽑는다
> (`--dynamic` 이 기본값).
>
> 이게 왜 중요하냐면, **크기를 박아둔 모델은 틀린 크기로 요청받아도 오류를
> 안 내고 자기 크기로 그냥 돈다.** 예전 기본값대로 640짜리가 나왔다면
> "OpenVINO 켜니 3배 빨라졌다"가 실은 "1280 대신 640으로 봤다"였을 것이다.
> **빠른데 틀린 결과**가 나오고 원인은 OpenVINO처럼 보인다.
> 그래서 이 카드를 켠 뒤에도 **반드시 4단계의 채점을 다시 돌려서
> `accepted=70` 을 확인한다.**

**①과 합치면 13~20초 추정치가 2~6초가 된다.** 여기서 끝날 가능성이 크다.

### ③ RAM 8GB

틱 시간이 들쭉날쭉하거나 디스크가 계속 돌면 **스왑이다.** CPU 문제가 아니다.
DDR4 SODIMM 한 개면 되고 슬롯이 2개다. **이 로드맵에서 가장 싼 위험 제거다.**

### ④ 크롭 재탐지 개수 줄이기 — 72칸 중 한 칸을 대가로 낸다

지금 **판단 시간의 63%를 크롭 재탐지가 쓴다** (노트북 3.3초 중 2.1초).

```bash
--max-crops 2      # 또는 1
```

**그냥 끄면 안 된다** (`--no-table-crops`). 끄면 70 → 67칸, 오답 2 → 5다.
개수를 줄이는 것만 여지가 있다.

### 하지 않을 것: `imgsz` 올리기

**측정해봤고 정확도가 오히려 떨어진다** (`plan.md` §2 결정 기록).

| 설정 | 옳음/72 | 틱당(노트북) |
|---|---:|---:|
| **현재 1280** | **70** | 3.3초 |
| 1536 | 68 | 3.5초 |
| 1920 | 69 | 4.0초 |

이 모델은 **640으로 학습**됐다. 1280도 이미 학습 크기의 2배라, 더 올리면
학습 때 본 적 없는 크기로 물체가 보여 못 맞춘다. **더 비싸고 더 나쁘다.**

## 막히면

| 증상 | 해결 |
|---|---|
| `ffmpeg를 찾지 못했다` | `which ffmpeg` 로 확인. 없으면 1단계의 apt를 다시 |
