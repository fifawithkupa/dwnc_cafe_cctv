# 엣지 박스 디코딩 측정 + 하드웨어 디코딩 (카메라 선정 근거)

> 작성: 2026-08-31
> 기준 커밋: `JINOI/main` = `6e71c31`
> 관련: `plan.md` T6·T9, `CLAUDE.md`

## 1. 배경

중고 미니PC(Intel 6세대 i3급)를 엣지 박스로 산다. **카메라는 아직 안 샀다.**
박스로 측정해서 두 가지를 정하는 것이 이 문서의 목표다.

1. **어떤 카메라를 살 것인가** (해상도 2MP / 4MP / 8MP, 코덱 H.264 / H.265)
2. 파인튜닝을 할 것인가 — 단, 이건 박스로는 안 나온다. §6 참조

## 2. plan.md의 전제 하나가 틀렸다

`plan.md` §2는 이렇게 적었다.

> **카메라 즉시 구매 — ❌ 엣지 벤치 후.** T6에서 나온 최대 프로파일이 있어야
> 해상도(2MP/4MP)를 제대로 고른다.

여기서 "T6의 최대 프로파일"은 `bench.py`가 내는 **추론** 속도표다. 그런데 추론은
프레임을 `imgsz`(640/960/1280)로 줄여서 모델에 넣는다 (`bench.py:96-118`). 즉
**카메라가 2MP든 4MP든 추론 시간은 사실상 같다.** 지금 `bench.py`만 돌려서는
해상도를 고를 근거가 나오지 않는다.

해상도가 실제로 잡아먹는 비용은 **디코딩** — 압축된 영상을 픽셀로 푸는 작업이다.
이건 tick마다가 아니라 **24시간 내내** 돈다. 그리고 지금 저장소에는

- 디코딩 비용을 재는 코드가 **없다**
- ffmpeg 호출 어디에도 하드웨어 디코딩 옵션(`-hwaccel`)이 **0건**이다
  (`seatnow_core.py:2899-2920`, `:2995-3019`, `:3064-3098`)

두 번째가 특히 문제다. 지금 상태로 재면 **소프트웨어 디코딩 숫자만 나오고**,
그 숫자로 카메라를 고르면 실제보다 훨씬 비관적으로 골라 4MP를 부당하게 탈락시킨다.

### 실측 (개발 노트북, 2026-08-31)

```
$ ffmpeg -benchmark -i sample_raw/cafe_sample_angle1.mov -t 10 -an -f null -
bench: utime=3.734s stime=0.453s rtime=1.126s
```

1080p H.264 영상 10초를 소프트웨어로 푸는 데 CPU 4.19초.
= **24시간 돌리면 코어 하나의 42%를 영상 푸는 데만 쓴다.** 최신 노트북 CPU에서다.
사려는 중고 i3는 이보다 몇 배 느리다.

**그러므로 T9(하드웨어 디코딩)가 T6(측정)보다 먼저다.** 순서를 뒤집는다.

## 3. 만드는 것

### A. `bench_decode.py` — 디코딩 측정 (신규)

#### A-1. 가짜 카메라 영상 생성

보유 영상은 전부 1080p이고 **14.9 Mbps**다. 실제 CCTV(2~6 Mbps)보다 훨씬 두꺼워서
그대로 재면 과대평가된다. 해상도와 비트레이트를 **둘 다** 실제 카메라 값으로 다시
인코딩해 `bench/clips/`에 캐시한다 (한 번 만들고 재사용).

| 이름 | 해상도 | 코덱 | 비트레이트 |
|---|---|---|---:|
| `2mp_h264` | 1920×1080 | H.264 | 4 Mbps |
| `2mp_h265` | 1920×1080 | H.265 | 4 Mbps |
| `4mp_h264` | 2560×1440 | H.264 | 6 Mbps |
| `4mp_h265` | 2560×1440 | H.265 | 6 Mbps |
| `8mp_h264` | 3840×2160 | H.264 | 10 Mbps |
| `8mp_h265` | 3840×2160 | H.265 | 10 Mbps |

화질은 가짜다(1080p를 늘린 것). **디코딩 비용은 진짜와 거의 같다** — 픽셀 수와
비트레이트가 같으면 푸는 비용이 같기 때문이다. 화질이 필요한 측정이 아니다.

**H.265를 같이 재는 이유**: 4MP 이상 카메라는 기본 코덱이 H.265인 경우가 많다.
H.265는 소프트웨어로 풀면 H.264보다 2배 가까이 비싸고, 하드웨어로는 비슷하다.
**"이 박스에서 H.265 카메라를 사도 되는가"가 실제 구매 결정 항목**이다.

#### A-2. 측정

각 클립을 `소프트웨어` / `하드웨어` 두 방식으로 디코딩하고, ffmpeg가 스스로 보고하는
CPU 사용량(`-benchmark`의 `utime`/`stime`)을 읽는다. 별도 라이브러리(psutil 등)를
추가하지 않는다 — 엣지 박스에 설치할 것이 하나라도 적은 편이 낫다.

측정값 = **영상 1초를 푸는 데 드는 CPU 초** = 상시로 점유하는 코어 수.

#### A-3. 판정

전체 코어 수 대비 비율로 등급을 매긴다.

| 등급 | 기준 | 뜻 |
|---|---|---|
| `PASS` | 전체 코어의 25% 이내 | 나머지 75%를 추론·OS가 쓸 수 있다 |
| `CONDITIONAL` | 25~50% | 돌긴 하는데 여유가 없다 |
| `FAIL` | 50% 초과 | 이 박스로 이 카메라는 못 쓴다 |

25%를 합격선으로 잡은 근거: `bench.py`의 tick 예산이 이미 **50% 이내**를 요구한다
(`plan.md` T6). 디코딩이 25%를 먹으면 추론 50% + 디코딩 25% = 75%로, OS·로그 회전·
RTSP 재연결 몫이 25% 남는다. 디코딩이 50%를 넘으면 추론 예산과 합쳐 100%를 넘는다.

#### A-4. 합산 판정

`bench.py`가 남긴 `bench/bench_report.json`이 있으면 읽어서 **추론 + 디코딩을 한
표로 합친다.** 그게 최종 구매 근거표다.

```
| 카메라 | 코덱 | 디코딩 | 추론(balanced) | 합계 | 판정 |
|---|---|---:|---:|---:|:---:|
| 4MP | H.265 | 18% | 46% | 64% | PASS |
```

### B. 하드웨어 디코딩 (`plan.md` T9)

`seatnow_core.py`에 입력측 ffmpeg 인자를 만드는 함수를 하나 두고, 세 군데의 ffmpeg
호출이 그것을 쓰게 한다. `seatnow.py`와 `bench_decode.py`에 `--hwaccel` 옵션 추가.
기본값 `auto`.

| 값 | 동작 |
|---|---|
| `auto` | OS에 맞는 후보를 순서대로 시도, 실제로 되는 것을 채택 (기본값) |
| `none` | 소프트웨어 디코딩 강제 |
| `qsv` `vaapi` `d3d11va` `dxva2` `videotoolbox` | 지정한 것만 시도 |

`auto`의 후보 순서:

| OS | 순서 |
|---|---|
| Windows | `qsv` → `d3d11va` → `dxva2` |
| Linux | `qsv` → `vaapi` |
| macOS | `videotoolbox` |

#### 설계상 가장 중요한 규칙: 조용히 넘어가지 않는다

ffmpeg는 하드웨어 디코딩 초기화에 실패해도 **경고만 내고 소프트웨어로 계속 도는**
경우가 있다. 안 켜졌는데 켜진 줄 알면 **벤치 숫자가 통째로 거짓말이 된다.**

그래서 `auto` 탐지는 후보마다 **실제로 프레임 한 장을 뽑아본다.** 프레임이 나온
것만 채택하고, 전부 실패하면 소프트웨어로 내려가되 **"하드웨어 디코딩 꺼짐"을
화면에 찍는다.** 탐지는 프로세스당 한 번만 하고 결과를 캐시한다.

이건 `CLAUDE.md`의 "판정 결과는 3상태로 정직하게 낸다"와 같은 원칙이다 —
모르는 것을 아는 척하지 않는다.

#### 인코딩(출력)은 손대지 않는다

`FFmpegVideoWriter`(`seatnow_core.py:3060`)는 주석 영상을 쓰는 디버그 경로다.
배포에서는 `--no-video`로 끄는 것이 기본이므로(`plan.md` T10, `CLAUDE.md` 개인정보)
하드웨어 인코딩은 대상이 아니다.

### C. `check_edge.py` + `docs/edge-setup.md` — 새 박스 세팅

`check_edge.py`: 박스에서 한 번 돌리면 항목별 합격/불합격을 **한국어로** 찍는다.
`CLAUDE.md`의 "설명은 비개발자 기준" 규칙을 따라, 불합격 항목마다 **무엇을 하면
되는지**를 같이 적는다.

검사 항목: ffmpeg·ffprobe 설치, 하드웨어 디코딩 실제 동작, Python 버전,
필요 패키지, CPU 모델·코어 수, RAM, 디스크 여유.

`docs/edge-setup.md`: **Windows 길**과 **Linux 길**을 따로 적어 복붙만 하면
"측정 두 줄"까지 간다. 리눅스 USB 만드는 법 포함. **OS는 지금 안 정해도 된다.**

#### OS 결정에 대한 기록

- **측정 단계**: 박스에 깔려 온 OS 그대로. 추론은 OpenVINO가 CPU에서 도는 것이라
  Windows/Linux 차이가 거의 없다. 리눅스 설치에 반나절 쓸 이유가 없다.
- **24/7 운영 단계**: Linux 권장. 성능이 아니라 **사고 위험** 때문이다 — Windows는
  강제 업데이트로 재부팅하고 로그인 화면에서 멈춘다. 무인 박스가 그러면 아침에
  좌석 정보가 죽어 있다.
- 하드웨어 디코딩 갈래를 함수 한 곳에 모으므로 **나중에 옮겨도 코드를 다시 안 쓴다.**

## 5. 제약

- Python 3.9 호환 유지 — `Optional[X]`/`Tuple[X, ...]`를 쓰고 `X | Y` 문법 금지
- 기존 테스트 229개는 계속 통과해야 한다
- 테스트는 `unittest`. ffmpeg 없이 도는 순수 로직 테스트가 기본이고,
  ffmpeg가 실제로 필요한 것은 건너뛸 수 있게 분리한다
- `AnalysisSettings`에 매장별 튜닝 파라미터를 추가하지 않는다 (`CLAUDE.md`)
- 생성한 벤치 클립은 `.gitignore` 대상 (`sample_raw/`와 같은 취급)

## 6. 이 문서가 답하지 못하는 것 — 파인튜닝

**파인튜닝 여부는 엣지 박스로 답이 안 나온다.** 박스가 알려주는 건 "얼마나 빠른가"고,
파인튜닝은 "모델이 이 카페를 얼마나 못 보는가"의 문제다.

그 답은 `plan.md` T14~T15에서 나온다 — 실영상을 돌려 UNKNOWN 사유 코드 분포를 보고,
`model` 그룹 비중이 크면 파인튜닝, `geometry` 그룹이 크면 카메라 각도를 다시 고른다.
**하드웨어 없이 노트북에서 오늘 할 수 있고, 아직 한 번도 한 적이 없다.**

그래서 §3-D(T14)를 이번 범위에 넣었다. 각도 선정(T15)과 라벨링(T16)은 사람 노동이
크므로 T14 결과를 보고 별도로 진행한다.
