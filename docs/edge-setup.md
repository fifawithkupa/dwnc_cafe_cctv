## 먼저 — 노트북에서 박스에 붙는 법 (SSH) 🖥️

**아래 1~9단계는 전부 이 방법으로 노트북에서 박스에 붙어서 쳤다.**
SSH = 노트북 창에서 치는 명령이 박스에서 실행되게 해주는 접속 방법이다.
박스에 꽂은 모니터로 직접 쳐도 되지만 그 화면은 **한글 글꼴이 없어서
한글이 전부 다이아몬드(◆)로 나온다.** 코드 문제가 아니라 그 화면의
한계다. SSH로 붙으면 한글도 보이고 복사·붙여넣기도 된다.
**모니터·키보드는 박스 주소를 알아낼 때 한 번만 쓴다.**

### ① 박스 모니터에서 — 사용자 이름과 주소 알아내기 (박스마다 다르다)

박스에 모니터·키보드를 꽂고 로그인한 뒤 이걸 친다.

```bash
echo "$(whoami)@$(hostname -I | awk '{print $1}')"
```

→ 이 박스는 **`hugo@192.168.0.39`** 다 (2026-09-06 확인). 이 문서의 명령은 전부
이 값으로 적혀 있다. **다음 매장의 박스는 다른 값이 나오니** 그때는 문서의
`hugo@192.168.0.39` 를 새 값으로 바꿔 친다.

### ② 노트북 PowerShell 에서 — 붙기

윈도우 시작 → `PowerShell` 검색해서 연다. 노트북과 박스가 **같은 공유기
(같은 와이파이)** 에 붙어 있어야 한다.

```powershell
ssh hugo@192.168.0.39
```

- **처음 한 번만** `Are you sure you want to continue connecting (yes/no)?` 가
  나온다 → `yes` 치고 엔터. (이 박스를 기억해두겠냐는 뜻이다.)
- `password:` 가 나오면 **박스 로그인 비밀번호**를 친다. **치는 동안 화면에
  아무것도 안 찍히는 게 정상이다.** 그냥 끝까지 치고 엔터.

→ 줄 맨 앞이 **`hugo@uhho:~$`** 로 바뀌면 붙은 것이다.
이제부터 이 창에서 치는 명령은 전부 **박스에서** 실행된다.

### ③ 알아둘 것

- **창이 두 종류다.** 붙어 있는 창(줄 앞이 `hugo@uhho:~$`) 은 박스,
  안 붙은 PowerShell 창(줄 앞이 `PS C:\...>`) 은 노트북이다.
  `scp` 로 파일을 보내는 명령(3단계 ②, 9단계 ③)은 **안 붙은 노트북 창**에서
  친다. 붙은 창에서 치면 "그런 파일 없다"고 나온다.
  헷갈리면 PowerShell 창을 하나 더 열어서 하나는 붙이고 하나는 그냥 둔다.
- **붙여넣기** — PowerShell 창에서는 **마우스 오른쪽 클릭**이 붙여넣기다.
  (Ctrl+V 도 대개 된다.) 이 문서의 명령을 복사해서 그대로 붙이면 된다.
- **끊기** — `exit` 치면 노트북으로 돌아온다. 그냥 창을 닫아도 된다.
- **노트북을 덮거나 창을 닫으면 끊기고, 박스에서 돌아가던 명령도 같이
  죽는다.** 7단계처럼 오래 도는 것을 걸어놓았으면 창을 그대로 둔다.
- **박스를 껐다 켜면(`sudo reboot`) 접속이 끊긴다.** 1분쯤 뒤 ②를 다시 친다.
  주소가 바뀌어 있을 수 있다 — 안 붙으면 ①을 다시 한다.
- **Claude 도 박스에 붙을 수 있다 (2026-09-06 등록).** 노트북에 열쇠 파일을
  만들어 박스에 등록해 두어서, Claude 가 노트북 터미널에서 비밀번호 없이
  `ssh hugo@192.168.0.39 "명령"` 꼴로 박스 명령을 돌리고 결과를 읽는다.
  그래서 박스 단계도 "네가 쳐서 결과를 붙여넣는" 대신 Claude 에게 시킬 수 있다.
  단 한 명령에 10분까지라, 그보다 긴 것은 뒤에서 돌게 걸어놓고 확인한다.
  박스를 새로 설치하면 등록이 사라지니 다시 한다: 노트북 PowerShell 에서
  ```powershell
  Get-Content "$env:USERPROFILE\.ssh\id_ed25519.pub" | ssh hugo@192.168.0.39 'mkdir -p ~/.ssh; cat >> ~/.ssh/authorized_keys; chmod 700 ~/.ssh; chmod 600 ~/.ssh/authorized_keys'
  ```
  (비밀번호를 한 번 물어본다. 열쇠 파일이 없으면 `ssh-keygen -t ed25519` 로 먼저 만든다.)

<details>
<summary><b>막혔을 때</b></summary>

- **`Connection refused`** — 박스에 접속 서버가 안 깔렸다. **박스 모니터에서:**
  ```bash
  sudo apt install -y openssh-server
  sudo systemctl enable --now ssh
  ```
  그리고 노트북에서 ②를 다시.
- **`Connection timed out`** 또는 한참 아무 반응이 없다 — 주소가 틀렸거나
  노트북과 박스가 다른 공유기에 붙어 있다. 박스 모니터에서 ①을 다시 쳐서
  주소를 확인하고, 노트북 와이파이가 같은 공유기인지 본다.
  (박스를 껐다 켜면 주소가 바뀌기도 한다.)
- **`hostname -I` 가 주소를 여러 개 뱉는다** — `192.168.` 이나 `10.` 으로
  시작하는 것을 쓴다 (같은 공유기 안 주소).
- **`Permission denied, please try again.`** — 비밀번호가 틀렸다. 3번 틀리면
  끊기니 ②를 다시 친다. 사용자 이름(`@` 앞)이 ①에서 나온 것과 같은지도 본다.
- **`WARNING: REMOTE HOST IDENTIFICATION HAS CHANGED!`** — 박스를 새로 설치했거나
  같은 주소에 다른 박스가 붙어서 노트북이 기억하던 것과 달라진 것이다.
  노트북(안 붙은 창)에서 기억을 지우고 ②를 다시 친다:
  ```powershell
  ssh-keygen -R 192.168.0.42
  ```
- **`ssh` 가 없는 명령이라고 나온다** — 윈도우 설정 → 앱 → 선택적 기능 →
  **OpenSSH 클라이언트** 를 추가한다. (윈도우 10/11 은 대개 이미 있다.)
- **아무리 해도 안 붙는다** — 박스 모니터에서 직접 친다. 한글이 ◆로 보일 뿐
  명령은 똑같이 된다. 파일 옮기기(3단계)는 USB로 한다.

</details>

## 3단계 — 영상 옮기기 ⚠️ **이건 노트북에서 친다**

**① 박스에서** (SSH로 붙은 창) 받을 폴더를 만든다.

```bash
mkdir -p ~/seatnow/sample_raw
```

②에 넣을 `hugo@192.168.0.39` 는 맨 위 "먼저" ①에서 적어둔 이 박스의
"이름@주소"다.

> ⚠️ **`mkdir` 을 건너뛰면 안 된다.** `sample_raw/` 는 용량·개인정보 때문에
> 저장소에서 제외돼 있어서 `git clone` 해도 안 생긴다. 그리고 `scp` 는
> **없는 폴더를 만들어주지 않는다.**

**② 노트북에서** — SSH로 **안 붙은** PowerShell 창을 하나 더 열어서 친다.
(붙은 창에서 치면 박스에서 노트북 파일을 찾으려다 "없다"고 나온다.)

```powershell
scp "C:\Users\jin06\orca\workspaces\dwnc_cafe_cctv\main\sample_raw\cafe_sample_angle1.mov" hugo@192.168.0.39:~/seatnow/sample_raw/
```

박스 비밀번호를 물어보면 입력한다. 146MB라 공유기 안에서는 1~2분.

→ 박스에서 `ls ~/seatnow/sample_raw/` 했을 때 파일이 보이면 된다.

USB로 옮겨도 된다. **AI 모델은 안 옮겨도 된다** — 5단계 ①에서 받는다.

<details>
<summary><b>막혔을 때</b></summary>

- **`Connection refused` · `timed out` · 비밀번호 거부** — 접속 자체가 안 되는
  것이다. 맨 위 "먼저"의 "막혔을 때"를 본다. 원인을 고친 뒤 `scp` 를 다시 친다.
- **`No such file or directory` 인데 노트북 파일 경로를 가리킨다** — SSH로
  붙은 창에서 쳤다. 안 붙은 노트북 창에서 친다.
- **`dest open "seatnow/sample_raw/": Failure`** 또는
  **`No such file or directory`** — 받을 폴더가 없다. ①의 `mkdir` 을
  안 한 것이다. 박스에서 `mkdir -p ~/seatnow/sample_raw` 하고 다시.
- **`mkdir` 을 했는데도 같은 오류** — `~` 를 못 풀고 있는 것이다.
  전체 경로로 친다 (`seatnow` 자리에 박스 사용자 이름):
  `... hugo@192.168.0.39:/home/hugo/seatnow/sample_raw/`
- **아무리 해도 안 붙는다** — 노트북과 박스가 **같은 공유기**에 붙어 있는지
  본다. 그래도 안 되면 **USB로 옮긴다.** 결과는 똑같다.

</details>

<details>
<summary><b>막혔을 때</b></summary>

- **하드웨어 디코딩 "꺼짐"** — 여기서 멈추고 잡는다. 꺼진 채로 재면 실제보다
  훨씬 나쁜 숫자가 나와서 멀쩡한 박스를 못 쓴다고 잘못 판단하게 된다. 순서대로:
  ① `groups` 에 `render` 가 있는가 (없으면 → 부록 B 재로그인)
  ② `vainfo` 가 `VAProfileH264...` 를 뱉는가
  ③ 1단계의 `-non-free` 드라이버를 깔았는가
  ④ **가상머신 안에서는 원래 안 된다**
- **한글이 전부 다이아몬드(◆)로 나온다** — **코드 문제가 아니다.** 박스에
  꽂은 모니터 화면(텍스트 콘솔)에 한글 글꼴이 없는 것이다. 확인: 같은 화면에서
  `echo "한글"` 을 쳐도 깨지면 화면 문제다. **노트북에서 SSH로 붙는다**
  (맨 위 "먼저"). 우분투 24.04 에서 이 도구들의 출력이 UTF-8 한글인 것은
  `LANG=C` 인 경우까지 확인했다 (2026-09-03) — 코드를 영어로 바꿀 이유가 없다.
- **메모리 3.7GB 불합격** — **그냥 진행한다.** 4GB를 꽂아도 운영체제가
  보고하는 값은 3.6~3.8GB다 (커널·내장 그래픽이 일부를 먼저 가져간다).
  2026-09-03 박스에서 실제로 3.7GB가 찍혔고, 검수 도구가 정확히 4.0으로
  자르던 것을 고쳐서 이제는 합격으로 나온다 (`git pull` 하면 반영).
  다만 **빠듯한 건 사실이다** — 7단계에서 틱 시간이 들쭉날쭉하면(4초↔20초)
  메모리 부족이니 그때 8GB로 늘린다.
- **`ffmpeg를 찾지 못했다`** — `which ffmpeg` 로 확인. 없으면 1단계를 다시.

## 9단계 — 카메라 고르기 ✅ **끝났다 (2026-09-06)**

**무엇을 재나.** 카메라 해상도가 잡아먹는 건 AI 판정이 아니라 **영상을
푸는 일(디코딩)**이다. 판정은 어떤 카메라든 화면을 1280으로 줄여서 보니까
2MP든 8MP든 시간이 거의 같다. 반면 디코딩은 **판정할 때만이 아니라
24시간 내내** 돌고, 화소 수에 비례해 무거워진다. 그래서 "이 박스가 어느
해상도까지 24시간 풀면서 판정도 제때 하나"를 잰다.

**카메라 없이 잰다.** 가진 카페 영상을 카메라 해상도·화질(2MP·4MP·8MP ×
H.264·H.265 = 6가지)로 바꾼 클립을 만들어서 박스에 풀게 한다. 화면은
늘려서 가짜지만, 푸는 비용은 화소 수와 비트레이트를 따르므로 진짜다.

**일이 두 곳으로 나뉜다.** 클립을 **만드는** 건 노트북, **재는** 건 박스.
박스는 코어 2개·4GB라 클립을 만들기엔 너무 느리고(노트북 8코어로 4분 45초,

**어디서 만들든 박스의 측정값은 같다.**

(숫자는 노트북 것이라 참고만):

```
## 결정 표 — 배포 설정만 (accuracy_default · ov-fp32)

| 클립     | 디코딩 방식 | 디코딩 | 추론 | 합계 | 판정 |
| 2mp_h264 | none        | 2%     | 4%   | 6%   | PASS |
| 2mp_h264 | vaapi       | 1%     | 4%   | 4%   | PASS |
| ...
| 8mp_h265 | none        | 12%    | 4%   | 16%  | PASS |
| 8mp_h265 | vaapi       | 2%     | 4%   | 6%   | PASS |
```

- **디코딩** = 영상 1초를 푸는 데 박스의 몇 %를 쓰나. 24시간 내내 이만큼.
- **추론** = 판정 한 번이 15초 주기의 몇 %를 쓰나 (①에서 잰 값).
- **합계 ≤ 75% → PASS**, 100%까지 CONDITIONAL, 넘으면 FAIL. 남는 25%는
  운영체제·스트림 재연결·로그 정리 몫이다.
- `none` 은 소프트웨어 디코딩, `vaapi`/`qsv` 는 하드웨어 디코딩이다.
  **둘의 차이가 1단계 드라이버의 값어치다.**

### 고르는 법

1. **결정 표의 하드웨어 줄(`vaapi` 또는 `qsv`)에서 PASS 인 것 중 해상도가
   가장 높은 것.** 같은 해상도면 **H.265** (같은 화질에 대역폭 절반).
2. **같은 클립의 `none` 줄도 본다.** 하드웨어 디코딩은 드라이버 업데이트나
   재로그인 문제로 어느 날 조용히 꺼질 수 있다 (부록 B). 그때는 `none` 값으로
   돈다. `none` 이 FAIL 인 카메라는 "드라이버가 살아있을 때만 되는 카메라"다.
   **`none` 까지 PASS 인 해상도가 안전한 선택이고, `none` 이 CONDITIONAL 이면
   그 위험을 알고 고르는 것이다.**
3. ⚠️ **이 박스에서는 CONDITIONAL 을 FAIL 로 읽는다.** 표는 코어를 4개로
   세는데(부록 A ③) 실제 연산 코어는 2개다. 하이퍼스레딩은 코어 2개 몫을
   못 하므로 표의 %는 실제보다 **최대 1.6배쯤 낙관적**이다. PASS 여유가
   그걸 흡수하고, CONDITIONAL 은 못 한다.
4. **RTSP 를 열어주는 기종인지 반드시 확인한다.** 하이크비전·다후아 계열은
   확정이고, 국내 저가 브랜드는 스펙 표에 "RTSP" 나 "ONVIF" 가 있는지 본다.
   막혀 있으면 위 측정이 전부 무의미하다 — 박스가 영상을 받을 방법이 없다.
   (`plan.md` §2)

> ⚠️ 합산은 **근사치다.** 판정이 도는 동안 코어를 전부 쓴다고 가정했다.
> 카메라를 탈락시키는 근거로는 충분하지만 3% 차이를 다투는 데는 못 쓴다.

<summary><b>막혔을 때</b></summary>

- **`unrecognized arguments: --build-only` / `--no-build`** — 박스(또는

- **④ 에 `ov-fp32 줄이 없어 pt 로 대신 보였다`** — ①을 5단계 변환 **뒤에**
  돌리지 않은 것이다. 배포는 OpenVINO 라 그 표로는 결정 못 한다. ① 부터 다시.
- **④ 에 `결정 표: 합산 판정이 없어 못 만든다`** — ①을 안 돌렸거나

- **④ 에 `하드웨어 디코딩 꺼짐`** — 4단계와 같은 문제다. 4단계 "막혔을 때".
  꺼진 채로 재면 `none` 줄만 나오고, 그건 실제보다 훨씬 나쁜 숫자다.
- **`qsv` 는 실패하고 `vaapi` 는 된다** — 괜찮다. 둘 다 하드웨어 디코딩이고
  자동으로 되는 쪽을 고른다.
- **④ 가 너무 오래 걸린다** — 8MP H.265 소프트웨어 디코딩은 이 박스에서
  실시간보다 느릴 수 있다 (노트북 8코어로도 3.5배속). 30초 클립 하나에
  1분 가까이 걸려도 정상이다. 급하면
  `--clips 2mp_h264 2mp_h265 4mp_h264 4mp_h265` 로 8MP 를 뺀다 —
  4MP 까지만 봐도 결정은 대부분 난다.
- **② 를 박스에서 돌리고 싶다** — 하지 마라. 4K H.265 는 막혀서 안 만들어지고

  4mp_h265 --duration 10` 으로 작은 것만 박스에서 만든다. 측정값은 클립
  길이에 비례하지 않으므로 10초여도 결과는 같다.

확정하면 `plan.md` §2 에 적는다. → **확정했다 (4MP·H.265·2.8mm).** 실시간으로

9단계에서 **4MP · H.265 · 2.8mm** 로 정해졌다. 그걸 박스에 붙이는 데
필요한 전부다. **합계 9만 원대**이고, 배송비는 별도다.

| 무엇 | 고른 것 | 값 | 어디서 |
|---|---|---:|---|
| 카메라 | 하이크비전 **DS-2CD1143G2-LIU 2.8mm** | 68,000원 | 네이버 스마트스토어 (알온테크) |
| 전원 공급기 | TP-LINK **TL-POE150S** | 15,900원 | [다나와](https://prod.danawa.com/info/?pcode=4730018) |
| 긴 랜선 (천장까지) | CAT.6 UTP 다이렉트 **30m** (예: NEXI NX-UTP630M) | 6,200원 | [다나와 검색](https://search.danawa.com/dsearch.php?query=CAT6+UTP+%EB%9E%9C%EC%BC%80%EC%9D%B4%EB%B8%94+30m) |
| 짧은 랜선 2개 | CAT.6 UTP 다이렉트 1~2m | 2,000원 ×2 | 같은 곳 |
| (선택) 케이블 몰딩 | 벽으로 선을 내릴 때만 | 5,000원 안팎 | 철물점·다이소 |

### 왜 이것들이 필요한가

**카메라는 랜선 하나로 전원과 영상을 같이 받는다.** 전원 어댑터를 따로 꽂지
않아도 되는 방식이라 천장에 콘센트가 없어도 된다. 그 전원을 랜선에 실어주는
장치가 **PoE 전원 공급기(인젝터)** 다. 카메라 값에 포함되어 있지 않아 따로 산다.

**둘이 맞는지 제조사 사양으로 대조했다 (2026-09-06).**

| | 카메라가 요구하는 것 | 인젝터가 주는 것 | |
|---|---|---|:-:|
| 규격 | IEEE **802.3af**, Class 3 | IEEE **802.3af** 준수 | ✅ |
| 전기 | 최대 **7.5W** | **15.4W** (48V 0.35A) | ✅ 두 배 여유 |
| 랜포트 속도 | 10/100Mbps | 10/100/1000Mbps 자동 | ✅ |
| 거리 | — | 최대 **100m** (우리는 30m) | ✅ |
| 영상 대역폭 | 최대 8Mbps | 100Mbps 로도 12배 여유 | ✅ |

> 카메라 쪽은 하이크비전 제품 페이지의 Power·Ethernet Interface 칸,
> 인젝터 쪽은 TP-Link(Omada) 제품 페이지에서 확인했다.

### ⚠️ PoE 인젝터를 고를 때 진짜 조심할 것 — "패시브"를 피한다

싼 인젝터 중에 **패시브(수동)** 방식이 있다. 규격을 무시하고 **꽂자마자
무조건 전원을 내보낸다.** 상대가 PoE 기기가 아니어도 보낸다 — 공유기나
박스에 잘못 꽂으면 **망가질 수 있다.** 값이 5천 원대로 유난히 싸다.

고른 TL-POE150S 는 **액티브(표준)** 다. 상대가 802.3af 기기인지 먼저
확인하고 맞을 때만 전원을 내보낸다. 잘못 꽂아도 아무 일이 안 일어난다.

**다른 제품을 살 때 구분하는 법:** 사양에 **`802.3af`** 와 **`자동 감지`
(auto detection / 자동 인식)** 가 둘 다 적혀 있으면 액티브다.
`PoE 지원` 이라고만 적혀 있거나 `패시브`, `24V` 라고 적혀 있으면 사지 않는다.
(표준 PoE 는 48V 다.)

**전원 어댑터는 인젝터 상자에 들어 있다.** 따로 안 사도 된다.

**연결은 이렇게 된다.**

```
매장 공유기 ──짧은 랜선── PoE 인젝터 ──긴 랜선 30m── 카메라 (천장)
     │                        └─ 콘센트에 꽂는다
     └──짧은 랜선── 엣지 박스
```

카메라와 박스가 **같은 공유기 안에** 있으면 된다. 인터넷 쪽으로 카메라를
열지 않는다 — 포트 포워딩도, 외부 접속도 만들지 않는다.

### 사기 전에 잴 것

- **인젝터에서 카메라까지의 실제 거리.** 천장으로 돌아가는 길이라 바닥
  직선 거리보다 길다. 여유 있게 재고, 애매하면 30m 를 산다. 남으면 감아둔다.
  (규격상 100m 까지 되므로 길어서 손해 볼 일은 없다.)
- **공유기에 빈 랜포트가 2개 있는지.** 인젝터용 1개, 박스용 1개.
  모자라면 스위치를 하나 더 산다 (1만 원 안팎).
- **인젝터를 꽂을 콘센트가 공유기 근처에 있는지.**

### 사지 말 것

- **카메라용 SD 카드.** 카메라에 영상을 저장하면 "영상 미저장" 개인정보
  예외 조항이 깨진다 (`plan.md` T10). 우리는 판정만 하고 영상을 남기지 않는다.
- **녹화기(NVR).** 박스가 그 일을 한다.
- **더 비싼 PoE 스위치.** 카메라 1대에는 인젝터로 충분하다.
- **8MP·6MP 카메라.** 더 싼 것이 있어도 사지 않는다 — 9단계에서 탈락했다.

### 카메라 상자에 들어 있는 것

천장에 다는 받침·나사·앵커·구멍 뚫는 종이본은 **카메라에 들어 있다.**
따로 살 필요 없다. 필요한 공구는 전동드릴과 드라이버뿐이고, 콘크리트
천장이면 콘크리트용 드릴날이 있어야 한다.

  비밀번호가 주소에 들어가야 한다: `rtsp://아이디:비밀번호@카메라IP:554/...`
- **틱 시간이 파일 모드(5.6초)보다 훨씬 길다** — 아래 "실측" ①이 그 경우였다.
  `--live-burst-seconds 0` 으로 돌리면 모든 프레임을 변환하는 옛 방식이다;
  기본값 5 가 맞다.
- **ssh 로 `pkill` 을 치다 접속이 끊긴다** — `pkill -f` 패턴이 ssh 명령줄
  자체와 겹치면 그 셸을 죽인다. 스크립트 파일(`run_live.sh`)로 돌리면 안 겹친다.

</details>

### ✅ 11단계 실측 (2026-09-06) — 실시간으로 60분씩 두 번

박스 안 가짜 카메라(4MP · H.265 · 30fps, 우리가 살 카메라와 같은 사양)로
15초 주기 판정을 **60분씩 두 번** 돌렸다. 둘의 차이는 디코더가 프레임을
어떻게 넘기느냐 하나뿐이다. 원본은 노트북 `results/live_box/`
(`*_report.json` · `*_summary.json` · 샘플러 CSV).

| | ① 모든 프레임 변환 (첫 구현) | ② 5초마다 5장만 변환 (**지금 코드**) |
|---|---:|---:|
| 틱 시간 평균 / p95 / 최대 | 5.62s / 6.81s / 9.52s | **3.52s / 3.58s / 3.65s** |
| 합격선(7.5s) 넘긴 틱 | 6 / 239 | **0 / 239** |
| 건너뛴 판정 슬롯 · 재연결 | 0 · 0 | 0 · 0 |
| 프레임 신선도 (틱 시작 때 가장 새 프레임의 나이) | 최대 0.11s | 최대 3.70s |
| 디코더(ffmpeg) CPU | **1.58코어** | **0.43코어** |
| 판정(파이썬) CPU 평균 | 1.02코어 | 0.39코어 |
| 박스 전체 CPU 평균 (물리 2코어) | 2.66 | **0.90** |
| 판정 프로세스 메모리 (워밍업 뒤) | 1,285~1,351MB · **+6MB/시간** | 1,267~1,278MB · **+2MB/시간** |
| ffmpeg 메모리 | 330MB | 283MB |
| 박스 남은 메모리 최소 | 1,499MB | 1,737MB |
| 하드웨어 디코딩 의심 | 없음 | 없음 |

**왜 ①이 느렸나.** 9단계 벤치의 디코딩 0.36코어는 `-f null` 로 **푸는 것만**
잰 값이다. 첫 구현은 30fps 전부를 BGR 로 바꿔 파이프로 넘겼고, 2560×1440
을 초당 30장 바꾸면 330MB/s 다 — 그 색변환·복사가 디코딩보다 비쌌다.
판정도 같은 코어를 뺏겨 5.6초까지 늘어났다. ②는 푸는 건 그대로 다 풀되(스트림은
건너뛸 수 없다) **틱에 쓸 5장만 5초마다** 바꾼다. 신선도가 최대 3.7초로
느슨해지는 대신 CPU 가 3분의 1로 준다. 15초 주기 판정에 3.7초 묵은 프레임은
문제가 아니다 (판정 확정에는 어차피 2~3틱이 걸린다).

**메모리는 새지 않는다.** 처음 600MB 에서 두 틱 만에 1,270MB 로 오르고
(OpenVINO 준비) 그 뒤로는 시간당 2~6MB 다. 노트북에서 같은 판정을 60번
반복해도 1,110MB 에서 평평했다. 4GB 박스에서 1.7GB 가 남는다.

**끊겼다 돌아오는 것도 확인했다.** 5분짜리 실행 도중 가짜 카메라를
죽였다 다시 켰다. 재연결 2회, **프레임 없음 틱 0개** (버퍼에 남은 프레임으로
판정을 이어갔다), 카메라가 돌아온 뒤 정상 복귀. 그 사이 기록에는
`last_error: Server returned 404` 가 남아 무슨 일이 있었는지 알 수 있다.

**9단계 결정 표와 맞춰보면.** 4MP H.265 의 24시간 실제 비용은 디코딩 0.43코어
(물리 2코어의 22%) + 판정 3.5초 (15초의 23%) = **약 45%**. 9단계에서 보정해
읽은 51% 와 같은 자리다. **4MP 확정은 유지**되고 여유는 더 있다. 8MP 는
실시간으로 다시 재지 않았다 — 9단계의 "드라이버 꺼지면 FAIL" 이 그대로다.

**설명 안 되는 것 하나.** ②의 판정 3.5초는 7단계 파일 모드(4.8초)보다
빠르다. 파일 모드는 틱마다 ffmpeg 를 새로 띄워 5장을 되감아 풀고, 그 뒤에
판정이 도는데도 그렇다. CPU 경합이나 클럭 차이(샘플러 평균 ①2333MHz vs
②1418MHz — 부하가 낮을수록 낮게 찍힌다)로 보이지만 확인하지 않았다.
합격 판단에는 어느 쪽 숫자를 써도 여유가 있어 파고들지 않았다.


### ✅ 11단계 추가 검증 (2026-09-06 오후) — 일부러 망가뜨려 보기

위 60분 측정은 "잘 될 때" 숫자다. 그 뒤 세 가지를 일부러 깨뜨렸고, 그 과정에서
**구멍 셋을 찾아 고쳤다.**

| 시험 | 결과 | 고친 것 |
|---|---|---|
| **드라이버 없이 (소프트웨어 디코딩, 4분)** | 틱 3.68s · 디코더 0.85코어 · 합격선 초과 0 | — (9단계 "꺼졌을 때 69%" 추정이 실측 66% 로 맞았다) |
| **카메라를 죽이고 그대로 둠 (3.5분)** | 죽인 뒤 **판정을 멈추고** 로그에 구멍(`gap`) 8개를 남김. 재연결 13회 시도 | ① 처음엔 버퍼에 남은 옛 화면으로 계속 "빈자리"를 냈다 → 판단 주기(15초)보다 오래된 화면은 없는 것으로 친다 |
| **하드웨어 디코더가 도중에 죽음 (4분)** | 경고 두 줄 찍고 **소프트웨어로 스스로 갈아탐**, 틱 3.4s 로 계속 | ② 처음엔 같은 명령으로 재연결만 반복해 영원히 프레임이 없었다 → 가속기 탓 + 재연결 중 + 새 프레임 없음이면 가속을 끄고 다시 붙는다 |
| 카메라 주소에 비밀번호 | 화면·기록·요약 모두 `rtsp://admin:***@...` | ③ 그대로 찍히던 것을 가린다 |

**부록 D·10단계에 적었던 "하드웨어 디코딩은 꺼져도 오류 없이 조용히 느려진다"는
절반만 맞았다.** 이 박스의 ffmpeg 6.1 은 `-hwaccel vaapi` 를 명시했을 때 가속이
죽으면 **조용히 느려지는 게 아니라 아예 죽는다** (`Hardware device setup failed`,
`Error opening output file`). 그러면 스트림이 끊긴 것과 구별이 안 됐다. 지금은
그 문구를 잡아서 갈아탄다. "조용히 느려지는" 경우는 **시작할 때** 자동 탐색이
실패해 소프트웨어를 고르는 경우뿐이고, 그건 시작 화면에 ⚠️ 로 크게 찍는다.

**소프트웨어 디코딩이 이제 합격선 안이라는 것도 새 사실이다.** 5초마다 5장만
변환하니 소프트웨어 디코딩도 0.85코어로 끝난다. 즉 4MP 카메라는 드라이버가
죽어도 판정이 밀리지 않는다 — 9단계의 "드라이버 살아있을 때만 되는 카메라"
경계가 4MP 에서는 사라졌다. (8MP 는 다시 재지 않았다.)

카메라를 죽였을 때 로그가 어떻게 생기는지 (앱은 이 구멍을 **모름** 으로 보여야 한다):

```
{"gap": true, "reason": "no_fresh_frames", "wall_clock": "...", "elapsed_s": 86.9,
 "live": {"reconnects": 6, "connected": false, "newest_age_s": 38.8,
          "last_error": "Error opening input files: Connection refused", ...}}
```

**진짜 카메라를 달면 다시 볼 것.** 이 측정은 박스 안에서 돌린 스트림이라
공유기·랜선·카메라 인코더는 빠져 있다. 재연결 간격(1·2·4·8·15초)과 소켓
타임아웃(10초)이 실제 카메라 재부팅 시간과 맞는지, 그리고 `프레임 없음`
틱이 하루에 몇 번 찍히는지를 본다.

## 12단계 — 자동 실행 (박스가 꺼졌다 켜져도 알아서 돈다) ✅ **설치됨 (2026-09-06)**

로그인하지 않아도 부팅 때 뜨게 했다. 사용자 그룹(render·video)이 그대로
따라오므로 하드웨어 디코딩도 된다.

### ① 박스에서 — 설치 (한 번)

```bash

```

처음 돌리면 `deploy/seatnow.env` 를 예시로 만들어 준다. **거기에 카메라
주소와 레이아웃을 적는다** (비밀번호가 들어가므로 git 에 안 올라간다):

```
SEATNOW_URL=rtsp://admin:비밀번호@카메라IP:554/Streaming/Channels/101
SEATNOW_LAYOUT=layouts/매장이름.json
```

지금은 시험대라 가짜 카메라(`rtsp://127.0.0.1:8554/seatnow`)를 가리키고,
가짜 카메라 자체도 서비스(`seatnow-fake-camera`)로 떠 있다. **진짜 카메라를
달면 가짜 카메라 서비스는 끈다:** `systemctl --user disable --now seatnow-fake-camera`.

# 부록

## A. 왜 그렇게 하나 (실측 근거)

### ① 로그의 `(CPU)` 를 실패로 읽지 말 것

내장 그래픽이 멀쩡히 잡힌 개발 노트북에서 위 7단계 명령을 그대로 돌려 비교했다.

| 실행 | 로그에 찍힌 장치 | 2번째 틱부터 |
|---|---|---:|
| 7단계 명령 그대로 (자동) | `(CPU)` | **619 ~ 643ms** |
| `--device intel:GPU` 를 붙임 | `GPU.0` | **644ms** |
| `--device intel:CPU` 를 붙임 (진짜 CPU) | `CPU` | **1964 ~ 2144ms** |

**자동과 그래픽 지정이 같은 속도이고 진짜 CPU는 3배 느리다** → 자동으로 두면
내장 그래픽을 쓴다. `(CPU)` 만 보고 "드라이버가 안 잡혔다"고 판단하면
멀쩡한 박스를 버리게 된다.

눈으로 꼭 확인하고 싶으면 2틱만 이렇게 돌린다:

```bash
./venv/bin/python -m engine.seatnow sample_raw/cafe_sample_angle1.mov \
  --layout layouts/cafe_angle1.json \
  --det-model yolov8n_openvino_model --pose-model yolov8n-pose_openvino_model \
  --device intel:GPU --max-samples 2 --no-video
```

`... inference on GPU.0...` 가 나오면 확실하다 (맨 처음 한 줄은 `--device` 를
줘도 `(CPU)` 다. **뒤의 두 줄**을 본다). 확인이 끝나면 `--device` 는 도로 뺀다.

### ② 틱 시간을 6으로 나누면 안 된다

`Completed 6 samples in Xs` 의 X 안에는 모델 굽는 첫 틱이 통째로 있다.

```
[  0.0s] ... inference=14748ms      ← 굽는 시간. 버린다
[ 15.0s] ... inference=643ms
Completed 6 samples in 20.1s
```

| 계산 | 값 | |
|---|---:|---|
| ❌ `20.1 ÷ 6` | 3.35초 | 첫 틱을 나머지 5번에 뒤집어씌운 값 |
| ✅ `(20.1 − 14.75) ÷ 5` | **1.07초** | 진짜 틱 시간 |

`inference=` 는 **영상 푸는 시간을 안 센다.** 24시간 도는 박스는 디코딩도
같이 하므로 **두 숫자를 다 적어둔다.** 위 예에서 1.07초 대 0.62초,
차이 0.45초가 영상을 푸는 값이다.

### ③ `check_edge` 의 "합격"을 곧이곧대로 믿지 않는다

- **"CPU 코어 수: 4개 합격"은 논리 코어다.** i3-6100T의 실제 연산 코어는 2개다
  (하이퍼스레딩은 코어 2개 몫을 못 한다)
- **RAM 4GB 박스는 "빠듯하다" 경고와 함께 합격이 뜬다** (실제 보고값 3.7GB)
- **openvino 는 아예 안 본다.** 확인하는 패키지가 numpy·cv2·torch·ultralytics
  넷뿐이라 openvino 가 없어도 "전부 합격"이 뜬다
- **이 박스의 진짜 판정은 검수 화면이 아니라 7·8단계의 실측 숫자다**

### ④ 드라이버가 두 종류다

| 드라이버 | 하는 일 | 확인 |

## F. 박스 코드를 최신으로 갱신하는 법 — `git pull`

노트북에서 고친 것을 박스에 반영하는 순서는 **딱 둘**이다.

```bash
# ① 노트북에서 — 박스는 main 에서 받아가므로 main 으로 민다
git push origin JINOI/main:main

# ② 박스에서
cd ~/seatnow
git pull
```

**이게 안전한지 우분투 24.04 에서 GitHub 를 흉내낸 저장소로 통째로 재현해
확인했다** (2026-09-03). 박스에 생기는 파일들 — `venv/`, `sample_raw/` 영상,
`yolov8n.pt`, `*_openvino_model/`, `results/edge_ov/log.jsonl`·`채점표.md`,
`results/edge/export_report.json` — 을 똑같이 만들어놓고 시험했다.

| 시험 | 결과 |
|---|---|
| 처음 받았던 옛 코드(90커밋 전) + 박스 파일들 → `git pull` | ✅ 성공. 박스 파일 9개 전부 그대로, 필요한 파일 전부 도착 |
| 노트북 커밋 → `main` 으로 밀기 → 박스 `git pull` (앞으로 매번 하는 흐름) | ✅ 성공 |
| 박스가 `git checkout JINOI/main` 을 해둔 상태에서 `git pull` | ✅ 성공 (어느 브랜치에 있든 된다) |
| 한글 이름 파일 (`layouts/cafe_sample_짐옮김.json` 등) | ✅ 제대로 받아진다 |
| **박스에 있는 미추적 파일과 같은 경로를 노트북이 커밋** | ⚠️ `git pull` 이 **멈춘다** — 단 박스 파일을 덮어쓰지는 않는다. 아래 |

**깨지는 경우는 하나뿐이고, 그것도 파일을 잃지는 않는다.** 예를 들어 박스가
만든 `results/edge_ov/채점표.md` 와 같은 경로를 노트북에서 커밋해 밀면 박스의
`git pull` 이 이렇게 거부한다:

```
error: The following untracked working tree files would be overwritten by merge:
        results/edge_ov/채점표.md
```

그러면 박스에서 그 파일 이름을 바꾸고 다시 pull 한다:

```bash
mv results/edge_ov/채점표.md results/edge_ov/채점표.박스.md
git pull
```

이걸 피하려면 **박스가 만든 결과 폴더(`results/edge_ov/`)를 노트북에서
커밋하지 않는다.** 노트북 결과는 `results/laptop_*` 처럼 다른 이름을 쓴다.

> `main` 은 **절대 force-push 하지 않는다.** 위 시험은 전부 fast-forward
> (역사가 이어지는 밀기) 전제다. 강제로 밀면 박스의 `git pull` 이 충돌로
> 멈추고, 그때는 박스에서 `git fetch && git reset --hard origin/main` 을
> 해야 하는데 이건 박스의 미커밋 변경을 날린다.

## E. 윈도우에서 돌릴 때

배포는 리눅스다 — 윈도우는 새벽에 강제 업데이트로 재부팅하고 로그인 화면에서
멈춘다. 무인 박스가 그러면 아침에 좌석 정보가 죽어 있고, 매장에서는 "앱이
고장났다"로 보인다. RAM도 1~1.5GB 더 먹는데 4GB에서는 그게 결정적이다.

개발 노트북 등에서 돌릴 일이 있으면 명령만 바꾼다:

- `./venv/bin/python` → `venv\Scripts\python.exe`
- 경로의 `/` → `\`
- ffmpeg 는 <https://www.gyan.dev/ffmpeg/builds/> 의 release full build 를
  `C:\ffmpeg` 에 풀고 `C:\ffmpeg\bin` 을 PATH에 넣는다
  (**넣은 뒤 명령 프롬프트를 새로 연다**)
- 하드웨어 디코딩은 인텔 그래픽 드라이버를 최신으로 올리면 켜진다
